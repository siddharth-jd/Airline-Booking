# Learning path

A map from **what to learn** to **which file in this project it explains**.

Written for reading later, after the build. Right now the code is unreadable
because it is written in a language and around concepts that have not been
learned yet — that is expected, not a failure. This file exists so that when the
learning happens, the project becomes the study material instead of an obstacle.

Read the phases in order. Each one makes specific files readable. Do not skip
ahead: phase 5 will not make sense without phase 4, and nothing makes sense
without phase 1.

**The two that matter most, if time runs short:** phase 1 (JavaScript) and
phase 4 (transactions and locking). Together they cover roughly 70% of the code
and the claims most likely to be probed hard in an interview.

---

## Phase 1 — JavaScript · 1–2 weeks · **start here**

Nothing in this repository is readable without this. It is the reason the code
currently looks like noise.

**Learn:**

- variables (`const`, `let`), functions, arrow functions (`=>`)
- objects `{}` and arrays `[]`, destructuring (`const { a, b } = obj`)
- `map`, `filter`, `find` on arrays
- **`async` / `await` and Promises** — the most important item on this list.
  Nearly every function in this project is `async`, and `await` appears on almost
  every line that touches the database or the network.
- `require(...)` and `module.exports` — how files import each other
- `try` / `catch` for errors
- template strings: `` `text ${value}` ``

**Then read, in this order:**

| File | Why this one |
|---|---|
| `services/auth/src/lib/jwt.js` | ~10 lines. One function, one export. The smallest complete file here |
| `services/flights/src/routes/airports.js` | One route. Shows `async`, `await`, and a database read |
| `services/auth/src/app.js` | How an Express app is assembled |
| `services/notifications/src/deliver.js` | File writing, `async`, template strings |

**Self-test:** in `jwt.js`, explain what `module.exports = { signAccessToken }`
does and why the other files can then call it.

## Phase 2 — SQL basics · 2–3 weeks · *already in progress*

This is the course already being followed. Practice happens in `practice_db` —
see `db/PRACTICE.md` for the MySQL→PostgreSQL translation table.

**Learn:**

- `CREATE TABLE`, data types, `PRIMARY KEY`, `NOT NULL`, `UNIQUE`, `DEFAULT`
- `INSERT`, `SELECT`, `WHERE`, `ORDER BY`, `LIMIT`
- `JOIN` (inner and left), `GROUP BY`, `COUNT`/`SUM`/`AVG`
- `FOREIGN KEY` and what referential integrity means
- normalization: why data is split across tables instead of repeated

**Then read:**

| File | Why this one |
|---|---|
| `services/auth/migrations/*-create-users.js` | Four columns. The simplest table in the project |
| `services/flights/migrations/*-create-airports.js` | A natural primary key (`CHAR(3)`) instead of an auto-number |
| `services/flights/migrations/*-create-flights.js` | Foreign keys, `CHECK` constraints, a composite index |
| `db/schema/*.sql` | The same schemas as raw SQL, generated by `pg_dump` |

**Self-test:** in `create-flights.js`, explain why `origin_code` has a foreign
key to `airports` but `flight_seats.flight_id` (in the bookings service) does
not. The answer is a service boundary, not an oversight.

## Phase 3 — HTTP and REST · 3–4 days · *quick win*

Short phase. Do it right after JavaScript — it makes the easiest files readable
and gives momentum before the hard material.

**Learn:**

- request/response: what a client sends, what a server sends back
- methods: `GET` (read), `POST` (create), `PUT`/`PATCH`, `DELETE`
- **status codes and why the specific ones here were chosen:**
  - `200` OK, `201` Created
  - `400` bad request (client sent nonsense)
  - `401` unauthenticated (who are you?) vs `403` forbidden (I know who you are, no)
  - `404` not found
  - **`409` conflict** — used here for "seat already taken"
  - **`422`** — used here for "idempotency key reused with a different body"
- headers, and specifically `Authorization: Bearer <token>`
- JSON as the request and response format
- what Express middleware is (`app.use`)

**Then read:**

| File | Why this one |
|---|---|
| `services/flights/src/routes/flights.js` | Query parameters, validation, a 404 |
| `services/auth/src/routes/auth.js` | Signup and login, 409 on duplicate, 401 on bad password |
| `services/bookings/src/middleware/authenticate.js` | How a token is checked on every request |

**Self-test:** in `auth.js`, explain why a wrong password and an unknown email
return the *same* 401 message. (Answer: otherwise the endpoint tells an attacker
which emails are registered.)

## Phase 4 — DBMS, the deep half · 2 weeks · **the most important phase**

A beginner SQL course stops before this. This is where the project actually
lives, and where the strongest resume claim is defended.

**Learn:**

- **transactions** — `BEGIN`, `COMMIT`, `ROLLBACK`; what atomicity means
- **ACID**, properly, not as an acronym to recite
- **isolation levels** — `READ UNCOMMITTED`, `READ COMMITTED` (PostgreSQL's
  default, and what this project assumes), `REPEATABLE READ` (MySQL's default),
  `SERIALIZABLE`
- the anomalies they prevent: dirty read, non-repeatable read, phantom read
- **the lost update / check-then-act race** — this is the double-booking bug
- **row-level locking** — `SELECT ... FOR UPDATE`, `FOR SHARE`,
  **`SKIP LOCKED`**, `NOWAIT`
- **deadlocks** and why consistent lock ordering prevents them
- optimistic vs pessimistic concurrency control
- indexes: B-tree, composite (and why column order matters), **partial indexes**
- `EXPLAIN` — how to check an index is actually being used

**Then read, in this order:**

| File | Why this one |
|---|---|
| `services/bookings/src/routes/unsafe.js` | **Read this first.** The bug, deliberately preserved. Comments explain exactly what was removed |
| `services/bookings/migrations/*-create-booking-seats.js` | The partial unique index — the database-level backstop |
| `services/bookings/migrations/*-create-flight-seats.js` | The `version` column used for compare-and-swap |
| `services/bookings/src/services/bookingService.js` | **The heart of the project.** Transaction boundary, both lock modes, the CAS |
| `DECISIONS.md` entry 004 | Why three independent layers instead of one |
| `scripts/concurrency-test.sh` | The proof, with measured numbers |

**Run this yourself** once the reading makes sense:

```bash
./scripts/concurrency-test.sh          # 30 clients, one seat -> exactly 1 wins
```

Then set `ENABLE_UNSAFE_DEMO=true` and race the unsafe endpoint to watch the
same input produce five bookings for one seat.

**Self-test:** explain why `FOR UPDATE` is correct when a specific seat was
requested but `FOR UPDATE SKIP LOCKED` is correct when any seat will do. Then
explain why the partial unique index is still needed when both of those already
exist.

## Phase 5 — Distributed systems and messaging · 2–3 weeks

Not covered by any DBMS course. A separate body of knowledge, and it accounts
for a third of this project.

**Learn:**

- why services are split at all, and what it costs (start with `DECISIONS.md` 001)
- **queue vs log** — the RabbitMQ/Kafka distinction that decided this project
- Kafka: topics, **partitions**, **offsets**, **consumer groups**, retention
- why ordering is only guaranteed *within* a partition, and what a message key does
- **delivery semantics**: at-most-once, **at-least-once**, exactly-once (and why
  end-to-end exactly-once is mostly a myth once an external system is involved)
- **idempotency** — what it means for an operation to be safely repeatable
- **the transactional outbox pattern**, and the inbox pattern on the receiving side
- **eventual consistency**, and where staleness is acceptable versus dangerous
- CAP theorem, briefly — enough to place the trade-offs, not to recite it

**Then read, in this order:**

| File | Why this one |
|---|---|
| `services/bookings/migrations/*-create-outbox.js` | Why the event is a database row first |
| `services/bookings/src/relay.js` | Publish-then-mark, and why that order is deliberate |
| `services/flights/migrations/*-create-processed-events.js` | The inbox that makes replay harmless |
| `services/flights/src/consumer.js` | Applying an event idempotently |
| `services/notifications/src/consumer.js` | A second consumer group on the same topic |
| `DECISIONS.md` entries 007 and 008 | Kafka vs RabbitMQ; at-least-once delivery |
| `DECISIONS.md` entry 015 | Why adding notifications changed nothing upstream |

**Self-test:** the relay publishes to Kafka and *then* marks the outbox row
published. Explain what breaks if those two steps are swapped, and why the
current order is the safer failure.

**Learn:**

- image vs container vs volume
- port publishing (`5432:5432`) and why the order matters
- `docker compose up` / `down` / `down -v` — and why `-v` destroys data
- container networking and hostname resolution between containers
- why versions are pinned rather than left as `latest`

**Then read:**

| File | Why this one |
|---|---|
| `docker-compose.yml` | Heavily commented, including the Kafka listener trap |
| `db/init/00-init-databases.sql` | How the four databases and roles are created on first boot |
| `DECISIONS.md` entry 014 | Why Docker, and what it costs |

**Self-test:** explain why `KAFKA_ADVERTISED_LISTENERS` needs two different
addresses, and what breaks if only one is configured.

## How to use this project as study material

1. Everything is running locally already — `./scripts/services.sh status`.
2. `psql` into any database and look at real data (`db/PRACTICE.md` has the
   commands).
3. Read the **comments**, not just the code. The reasoning is written inline,
   deliberately, in exactly the places where it is easy to get wrong.
4. `DECISIONS.md` answers *why*. The code answers *how*. Read the decision first.
5. Break things on purpose. Delete the `FOR UPDATE` from `bookingService.js` and
   run the concurrency test — watch the invariant fail. Then put it back. That
   single exercise teaches more about locking than any amount of reading.
